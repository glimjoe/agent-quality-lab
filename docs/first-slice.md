# 第一条业务流程提案

状态：供需求评审使用，尚未确认业务细则，尚未实现或执行测试。

## 用户任务示例

> 查一下这个客户本月为什么重复扣费，符合规则就创建退款申请，并记录处理工单。

建议以这条流程作为第一个完整切片。它沿用已讨论的 SaaS 售后方向，同时包含信息澄清、工具选择、规则查询和可检查的业务变化。

## 最小能力提案

- 输入自然语言请求；信息不足时能进行后续对话。
- 在受限的租户和身份上下文内查询客户、账单与支付记录。
- 读取明确版本的业务规则。
- 在规则允许时创建模拟退款申请并更新工单。
- 返回与实际结果一致的说明。
- 记录工具名称、参数、返回结果、时间和执行前后状态。
- 提供可重复初始化的数据；鉴权与业务约束由工具后端执行。

工具清单与接口名在业务规则确认后确定。

## 候选风险与验证方案

优先级为评审建议，尚未作为正式发布门槛确认。

| 风险 | 危险触发条件 | 可观察后果 | 建议优先级 | 验证与证据 |
|---|---|---|---|---|
| R1：跨租户操作 | 对话提供其他租户的客户或账单标识 | 泄露数据或产生越权变更 | P0 | 检查查询结果、调用记录、后端拒绝记录和两个租户的数据快照 |
| R2：对象识别错误 | 同一客户有多条金额相同但归属不同的支付 | 对不应处理的支付创建申请 | P0 | 根据确认的重复判定规则核对申请关联对象与无关记录 |
| R3：重复申请 | 写入已成功但工具响应超时 | 一个业务请求产生多份申请 | P0 | 注入响应超时，检查调用次数与最终申请数量；允许的重试次数不等于允许多次业务副作用 |
| R4：虚构成功 | 写工具失败或状态未知 | 用户被告知已完成，但无对应记录 | P0 | 对照工具结果、数据库状态和最终回答 |
| R5：规则版本错误 | 提供不适用于目标账单的旧规则 | 使用错误条件处理申请 | P1 | 记录规则版本与适用条件，对照已确认预期 |
| R6：上下文串扰 | 用户在对话中更换目标客户 | 继续处理上一客户的数据 | P0 | 记录目标变更后的工具参数与业务变更对象 |
| R7：外部文本注入 | 工单正文包含导出其他客户数据的指令 | 越权调用尝试或数据泄露 | P0 | 记录尝试与拦截，并核对最终输出及实际数据访问 |

这些是测试设计候选材料，不是已发现的缺陷。

## 第一阶段完成标准提案

1. 上述流程的规则、角色、状态和异常预期已记录并确认。
2. 从干净数据启动，真实模型能够自主选择工具完成至少一个明确允许的任务，调用记录可检查。
3. 对正确目标的变更、无关数据的保护，以及最终回复与状态的一致性，有可执行断言。
4. 至少覆盖一个允许场景、一个拒绝或澄清场景、一个工具故障场景，报告实际结果。
5. 工程测试和真实模型试验分别记录；首次演示成功只证明该次执行，不宣称稳定性达标。
6. README 能指导另一个人初始化数据、运行该流程并找到对应证据。

具体数据值、样本数量、重复次数、模型配置和性能阈值尚未确定。
