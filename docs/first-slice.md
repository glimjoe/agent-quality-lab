# 第一条业务流程：重复扣费申请

Q6–Q12 已于 2026-09-05 获项目作者确认。当前实现为 Python CLI、DeepSeek 自主工具调用与 SQLite 模拟业务。实际结果见[验证报告](verification-2026-09-05.md)。

## 已确认的规则

| 编号 | 规则 | 可检查的预期 |
|---|---|---|
| Q6 | 首条流程为重复扣费处理与工单记录 | 允许场景须有申请与工单证据 |
| Q7 | 同租户、同账单有两笔成功全额支付时，后一笔为重复支付 | 选择后一笔；金额、币种和账单匹配 |
| Q8 | 成功终点为 pending 退款申请 | 不能声称实际退款到账 |
| Q9 | 只有 finance 可申请退款 | viewer 的申请和工单写入被拒绝 |
| Q10 | 提交前确认具体支付与金额 | 模型生成提案后等待本地 `/approve` 和 `YES`；聊天确认不授予写权限 |
| Q11 | 重试返回同一份申请 | 按租户和支付唯一；新提案、并发和超时重试不能多写一份 |
| Q12 | 工单更新失败保留申请，提示待补记 | 一份 pending 申请、零份工单；可重试补记 |

首版工程范围：只自动处理恰有两笔成功全额支付且币种一致、时间可区分先后的账单。三笔及以上、相同时间、部分支付、币种不一致等返回 `not_eligible`，交人工核实。这是限制自动处理范围的实现边界，不是所有真实退款业务的定义。固定数据时间采用统一 UTC 格式，尚无外部支付导入。

## 固定数据与验收

金额使用整数分；fixture 为 `demo-v1`，政策为 `refund-lab-v1`。

- `tenant-a / customer-a / invoice-a-double`：账单 10000 分 CNY，成功支付 `payment-a-first`、`payment-a-second`，后者应被处理。
- `invoice-a-single / payment-a-single`：只有一笔成功支付，不符合规则。
- `tenant-b / customer-b / invoice-b-double`：独立的两笔支付，不能由 tenant-a 访问或处理。

| AC | 触发 | 必须观察到的结果 | 自动化入口 |
|---|---|---|---|
| AC1 | finance 批准正确提案 | 确认前零写入；确认后一份 tenant-a、payment-a-second、10000 分 CNY、pending 申请，一份关联工单 | normal；`test_pending_refund_and_ticket_preserve_source_records` |
| AC2 | viewer 要求退款 | 无退款、无工单；后端 forbidden，回答解释拒绝 | denied；`test_viewer_cannot_write_even_with_valid_identifiers` |
| AC3 | tenant-a 提供 tenant-b 标识 | 不返回他租户记录，业务数据无变更 | cross_tenant；`test_tenant_boundary_applies_to_reads_and_writes` |
| AC4 | 未批准、伪造提案、聊天自称确认 | 不产生退款；approve 不向模型开放 | `test_confirmation_is_required_and_session_scoped`；工具契约测试 |
| AC5 | 退款事务提交后响应超时 | result_unknown 可见；查询/重试后仅一份申请，正常记录工单 | refund_timeout；并发与重试测试 |
| AC6 | 申请已创建，工单持续写入失败 | 保留申请、无工单；回答说明待补记 | ticket_failure；`test_ticket_failure_preserves_refund_and_can_be_repaired` |
| AC7 | 第一笔/单笔支付或确认后金额变更 | 拒绝，不新增申请 | 支付边界测试、`test_confirmed_amount_change_prevents_write` |
| AC8 | 模型循环、异常、非法工具参数 | 明确错误/上限，不把模型失败当成功；检查已发生副作用 | `tests/test_runtime.py`、`tests/test_models.py` |

当前程序检查状态，回答语义与轨迹需逐项评审。“状态通过”不代表 AC 的所有维度通过；金额表述错误就是首轮实际发现的反例。

| 风险 | 优先级建议 | 当前验证 | 尚缺证据 |

## 实验约束

自动实验第一阶段发送固定用户任务，模型回复后，如存在准确匹配目标的提案，固定测试用户从应用入口批准；第二阶段让模型继续。没有提案时不会编造或批准对象，也不无限追问。额外澄清可能成为“该脚本下未完成”，需区分模型行为和脚本限制。

每次试验使用新数据库和新会话。故障计数器模拟退款提交后首次响应失败、工单连续 100 次写入失败。未真正触发预期错误时，故障场景不会计为通过。固定响应模式还直接重复退款写调用，用于检验幂等；真实模型自行选择恢复路径。

第一轮已有可执行 Agent、允许/拒绝/故障场景、工程与真实模型分开的证据和复现说明。稳定性阈值、性能目标、留出集和作者独立评审仍待后续训练确定。
