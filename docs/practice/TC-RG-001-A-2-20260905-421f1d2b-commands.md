# Local confirmation and conflict rules

Status: `[LOCAL]`

Use only when the user explicitly requires confirmation for every uncertainty, or when source, code, screenshot, environment, or scope evidence conflicts.

## Strict confirmation mode

When the user says "do not guess", "confirm every uncertainty", or equivalent:

1. Number every unresolved question continuously.
2. Ask one specific decision per question.
3. State the affected scope or output.
4. Wait for an explicit answer before continuing the affected branch.
5. Record confirmed answers and their source.
6. Continue scanning for new uncertainty until the user says there are no more questions or authorizes completion.

Use the user-input mechanism available in the current environment. Do not require a tool by a hard-coded name.

Do not treat "probably", "roughly", or a partial answer as confirmation.

## Conflicting descriptions

When two statements require mutually exclusive behavior:

1. Quote or accurately identify both statements.
2. Explain the contradiction.
3. Stop analysis that depends on the conflict.
4. Ask which statement is authoritative.
5. Record the answer and reject the other statement for the current version.

Do not merge incompatible behaviors into a compromise rule.

## Unspecified "other cases"

When a requirement states "when A, do B" but says nothing about non-A:

- identify the missing branches;
- ask whether they keep current behavior or adopt a new default;
- ask what "current behavior" contains when it has multiple branches;
- decide whether regression evidence is required;
- keep all proposed non-A behavior yellow until confirmed.

## User interpretation versus source

When the user's interpretation differs from the authoritative material:

1. show the source statement and the interpretation;
2. identify the difference;
3. ask which one governs the current output;
4. if the user chooses their interpretation, label it as user-confirmed rather than source-derived.

## Code versus requirement

When implementation and requirements differ:

- do not assume either is correct;
- show the implementation behavior and requirement behavior;
- ask which should govern;
- record the decision before generating dependent cases or conclusions.

## Unfamiliar terms and outcome-equivalent existing capabilities

When a requirement uses an unfamiliar business term, do not decide that a feature is missing merely because the code has no matching button, route, state, class, or method name.

1. Translate the term into observable business outcomes and invariants: actor, preconditions, trigger, state transition, persisted result, downstream effect, retry behavior, and limits such as count or uniqueness.
2. Search the current implementation by those behaviors and state transitions, not only by the requirement's literal wording.
3. Check both a single existing function and a reachable combination of existing functions.
4. Compare whether the existing path preserves the same actor, preconditions, final result, failure behavior, and business invariants.
5. Check whether the requirement explicitly mandates a particular interaction, dedicated entry, role, permission, audit event, or technical mechanism.

Classify the result:

- **Existing equivalent capability:** current code directly supports the same observable result and invariants, and the confirmed requirement does not mandate a specific mechanism. Treat it as existing behavior or compatibility regression, not a missing new feature.
- **Candidate equivalent capability:** the code supports only part of the result, or product intent is unclear. Keep it yellow, show the evidence, and ask one focused confirmation question.
- **Not equivalent or not found:** a required result or invariant cannot be achieved. Trace the gap to the requirement rather than to the absence of a same-named implementation.

Code can establish what the current system is capable of; it cannot by itself establish whether product intent requires a distinct user experience or named mechanism. If the user or authoritative source confirms that observable business results govern, a matching existing function or function combination is sufficient. If a dedicated interaction or mechanism is explicitly required, outcome equivalence alone is insufficient.

## Environment differences

Keep test and production evidence separate. Identify configuration, topology, data source, device, replication, and external-service differences.

When the test environment cannot reproduce a production-only risk:

- state the limitation;
- lower the supported evidence conclusion;
- define pre-production or production verification;
- add an observation item, threshold, owner, and contingency action.

Do not read a production environment when the authorized scope is test-only.

## Multi-stage reports

The final report must preserve confirmed scope, ACs, risks, questions, and evidence from earlier stages. Add later code or execution findings; do not replace earlier analysis with a short summary that loses traceability.
