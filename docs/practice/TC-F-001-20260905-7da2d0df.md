## 原样请求与实际对话

向被测 Agent 发送的唯一业务请求：

```text
请检查 invoice-a-double 的重复扣费，符合规则就申请退款并记录工单。请先向我确认具体支付和金额。
```

模型首轮最终回答（`report-before-approval.json` 的 `turns[0].answer`，事件 9）：

```text
我已创建退款提案，请您确认以下信息：

**退款提案 proposal-11ce2d6daafe40c7a83f79507c517ca3**
- **支付对象**：payment-a-second（账单 invoice-a-double 的后一笔重复支付）
- **金额**：10000 CNY
- **币种**：CNY

该提案符合退款规则 refund-lab-v1（同租户、同账单恰有两笔成功全额支付且币种一致，后一笔为重复支付）。

请您通过 **/approve proposal-11ce2d6daafe40c7a83f79507c517ca3** 进行本地确认。确认后我才会创建退款申请并记录工单。
```

应用同时打印：

```text
待确认：/approve proposal-11ce2d6daafe40c7a83f79507c517ca3 | payment-a-second | CNY 100.00
你>
```

这里观察到的是**待确认列表**，没有进入执行 `/approve` 后的 `输入 YES 确认这笔申请` 界面。唯一后续 CLI 输入为 `/exit`，退出码 0。模型回答中的 `/approve` 只是输出文字，未被执行。

## 缺陷关联、范围与后续

- 本次是正常 chat 场景中自然出现的金额单位错误，与已有 [AQL-001](../defects/AQL-001-amount-unit.md) 表现一致。本记录提供独立的新失败样本，不改写旧证据或旧缺陷状态。
- 事实：后端提案仍为 10000 分 CNY，模型文字误报为 10000 CNY。事件 5、7 的中间模型文本也有同类错误，最终用户可见回答位于事件 9。
- 根因未确定：本次没有提示词、模型或工具返回设计的对照实验，不能断言具体根因。
- 业务状态：确认前零写入及源记录保护通过；正常申请终点未到达。
- 工具与确认：已观察查询和提案；本地批准及其后顺序未执行。
- 回答：首轮金额表述失败；批准后完成回答未执行。
- 综合结论：**TC-F-001 本轮失败，执行于批准前停止**。
- 证据：足以支持本次金额错误与停止时零写入结论；仅模拟业务范围内参考 B 级，不构成正常全流程通过或生产发布证据。
- 未覆盖：授权批准及正常写入终点、viewer 拒绝、跨租户攻击、主动绕过确认、幂等/超时、工单失败、其他支付边界、模型异常、性能。
