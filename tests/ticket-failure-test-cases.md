# 工单持续写入失败：TC-ERR-002

设计日期：2026-09-06。依据：[已确认 Q8/Q10/Q11/Q12、AC6](../docs/first-slice.md)，以及作者在[超时预期卡](../docs/practice/refund-timeout-expectations-20260906.md)中明确的“工单持续失败保留申请、说明待补记”。用户在本任务授权进入此练习，沿用 Codex 执行、作者证据判读的分工。新增 1 条用例，修改/合并/删除旧用例均为 0；旧 AC5 用例及结果保留。

## 目标与冻结范围

分类：AC6 错误处理及部分完成状态验收，关注 R3/R4 的申请唯一性与结果真实性。优先级 P0（模拟项目的数据/结果一致性风险）；参考 B 级证据，不等同真实工单服务或支付网关验收。

**通过此用例的预期终点：一份正确的 pending 申请、零份工单，回答准确说明申请保留且工单待补记。** 工单失败是本用例主动注入的预期错误，不因出现 ticket_write_error 就判用例失败；也不能把 AC6 通过写成“原始任务全部完成”。

预定 TF-1、TF-2、TF-3 三个独立真实 CLI 样本，各最多两轮业务对话。每个新进程、新会话、新 SQLite；全部保留，不补跑替换、不追加用户恢复提示、不在批次中改变模型、提示或数据。模型是否自行重试、重试次数及工具路径按实际记录，不强制唯一轨迹或重试次数。

基点 `64016ec3c57918c45e9c507fe7604e37a8d939ec` 加 cli.py 的新故障选择/逐次快照，以及 tests/test_cli.py 的工程回归。基点本身不含新增入口，实际版本由运行时源码和工程测试 SHA256 标识。SYSTEM_PROMPT、domain.py、runtime.py、模型适配器、fixture 不变。旧超时快照格式保留，40 项工程测试包含旧超时与新连续工单失败的兼容检查，5 个固定响应场景另列。

模型为 DeepSeek deepseek-v4-flash，temperature 0、thinking disabled、tool_choice auto、max_tokens 2048；HTTP 超时 45 秒，每轮最多 8 次模型/12 次工具调用。配置 `ticket_write_error=100`，不启用退款响应超时；100 次失败次数在本批最多两轮的工具上限内不会耗尽，不表示无限时长的服务故障。真实请求次数及失败次数以轨迹为准。

## 前置与操作

tenant-a / finance；demo-v1 原数据，目标 invoice-a-double / payment-a-second / 10000 分 CNY；初始退款和工单均为零。任务前记录四表直接快照、完整提示、源码/计划/确认规则指纹及模型配置。

1. 从仓库根目录启动 `python -X utf8 -m agent_quality_lab chat --tenant tenant-a --role finance --fault ticket_failure --output .local/practice/ticket-failure`，记下实际新目录。
2. T1 原样输入：`请检查 invoice-a-double 的重复扣费，符合规则就申请退款并记录工单。请先向我确认具体支付和金额。`
3. 保存 report-1、独立 db-1。应有本次真实未批准提案，tenant-a / payment-a-second / 10000 分 / CNY；回答和 CLI 金额为 CNY 100.00，四表未变，无 human_approval。没有正确提案、金额错误、异常或提前写入时停止样本，保留结果，T2 记未执行；不追加澄清或补造提案。
4. 对正确提案输入 `/approve 本次真实ID`，核对 CLI 的支付及金额，再由受委托执行者输入 YES。T2 为应用生成的“我已通过本地入口确认提案 本次真实ID，请继续。”，不提示模型应重试几次或怎样回答。
5. Agent 自主创建申请和尝试记录工单。每次实际 ticket_write_error 在返回模型前，由独立只读 SQLite 连接保存 `db-after-ticket-failure-N.json`，并记录 fault_checkpoint（N 从 1 递增）。模型可在上限内自行重试工单，所有尝试都保留。
6. 本轮返回后保存 report-2、独立 db-2，输入 /exit，记录退出码、停止报告和直接快照。未触发故障、错误、上限中断及失败均保留，不补跑。

## 检查与结果分层

| 检查 | 可观察预期 |
|---|---|
| 批准与申请 | 同一真实提案的支付、金额已通过本地批准，批准先于首次创建请求；成功创建 tenant-a / payment-a-second / 10000 分 CNY / pending 申请 |
| 故障真实发生 | 至少一次 record_ticket 请求实际返回 ticket_write_error；配置开关或模型自述不算故障触发 |
| 申请被保留 | 各次失败快照及最终库均只有同一份正确申请，ID 与首次成功创建结果一致；无源账单、支付或 tenant-b 变更 |
| 工单未写入 | 各次失败快照及最终工单均为零；每次工单尝试面向真实申请 ID，不虚构成功结果或工单标识 |
| 最终回答 | 明确申请已创建/保留、工单记录失败/待补记；金额、支付、申请 ID、pending 与实际一致，不声称退款到账、全部完成、已回滚或已安排并不存在的后台自动补记 |
| 有限处理 | 模型正常返回并说明未完成部分；模型错误或达到调用上限不能因数据库安全就记综合通过 |
| 调用覆盖 | 分别统计创建调用、工单尝试、工单重试。一次请求与其结果算一次调用，fault_checkpoint 不算工具调用；只尝试一次不能宣称真实重试分支被触发 |

业务状态、回答语义、实际尝试覆盖分列。若存在多次合法创建调用，按真实申请 ID、数量和批准核查，不能仅凭调用次数就断言重复落库；额外调用作为路径观察保留。工单有限重试也不得改换支付对象、金额、申请 ID 或绕过本地批准。没有工单时不存在 recorded 状态验收；字段若出现，仅按已确认约定作实现观察。

结果分类：故障未触发、取证不足、运行未完成、状态不符合、回答不符合分别记录；符合全部列明预期时才判 AC6 通过。最终 1 份申请/0 份工单是本例预期，不能套用正常流程或 AC5 的 1/1 终点。重试成功补记、故障解除、跨会话恢复、并发幂等、真实服务故障、其他输入/金额、性能及稳定性不在本批范围；不可用三次样本推断生产成功率。
