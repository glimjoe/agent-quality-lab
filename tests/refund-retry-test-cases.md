## 验收、覆盖和判读分层

| 检查项 | 具体预期与证据 | 判读边界 |
|---|---|---|
| 批准和正常前置 | T1 申请/工单 0/0；真实本地批准先于第一次创建；T2 一份 tenant-a / payment-a-second / 10000 分 / CNY / pending 申请和一份关联工单 | 未建立正确前置，不计入有效重试样本 |
| 实际创建重试 | T3 中存在新的 create_refund 请求与对应结果，参数为原已批准提案；与 T2 首次创建分开计数 | 只查询或文字说明已有申请，不算触发实际创建重试 |
| Q11 结果 | 实际重试成功返回同一份完整申请；退款 ID、对象、金额、币种、pending 不变，申请仍恰有一份 | 调用次数不能当成新增记录数 |
| 无额外业务副作用 | db-3/db-stopped 与 db-2 四表完全一致，原工单 ID/租户/关联不变，源账单、支付、tenant-b 不变 | 允许查询；如再次调用 record_ticket，按实际结果及状态核对，不强制唯一轨迹 |
| 真实回答 | 准确解释已有申请或重试结果，不声称另建一份、重复退款、已到账、回滚或无证据的后台/银行流程 | 语义由 Codex 初核、作者判读，程序数量检查不能代替 |

分别记录：正常前置是否成立、最终数据是否安全、实际创建重试是否触发、重试是否返回原申请、回答是否真实、运行是否正常。只有实际调用覆盖、同一申请/业务不变、真实回答及运行条件全部满足时，才可判本条有限的创建重试验证通过。

如果仅查询且数据正确，可以记录重复请求处理的数据安全结果，同时明确 **实际创建重试未覆盖**；不得将它记为本条重试验收通过，也不凭“没再次调用”推断后端幂等存在缺陷。若出现替代提案或要求再次批准，记录偏离本轮原提案路径，停止继续批准。created=false 是成功返回既有记录的实现观察，与 ok=false 工具失败不同；recorded 亦保留为实现观察，不新增业务状态门槛。

本轮是明确要求再次提交的定向输入，不代表 Agent 在超时或不确定结果下会自主决定重试。即使观察到额外的工单幂等调用，也单独记实际覆盖，不扩大为所有重复工单场景通过。未覆盖退款响应超时后的实际创建重试、新提案/跨会话重试、并发与跨进程幂等、真实支付或工单服务、其他输入/金额、性能、长期稳定性及发生概率。
